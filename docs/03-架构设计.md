# 03 · 架构设计

## 1. 设计原则

1. **抓取只有一份**：所有来源与解析器都在 `gacha-calendar-core`；本仓库不复制解析逻辑。
2. **UI 只读数据**：界面层不理解"怎么抓"，只消费冻结的 Result JSON。
3. **先能验证再谈优雅**：v0.1 用应用外的 Node 脚本产出快照，先把"任务栏窗口 + 真实数据"跑通；
   应用内抓取（WebView2 CoreHost）放到 v0.1.7，不阻塞产品验证。
4. **任务栏只做"覆盖"，不做"注入"**：见 [02-调研](02-Windows11任务栏集成调研.md)。
5. **失败必须可见**：某列失败就标失败，不允许把旧数据当最新数据静默展示。

## 2. v0.1 数据流（当前）

```
┌──────────────────────────────┐
│ tools/refresh.mjs（Node 22）  │
│  fetchRaw / fetchViaProxy     │
│  storage（内存 Map）           │
└──────────────┬───────────────┘
               │ import（npm 依赖）
               ▼
     gacha-calendar-core@0.12.x
     （28 款游戏 · 解析器 · 刷新编排 · 失败降级）
               │ Result JSON（schemaVersion=1）
               ▼
     data/snapshot.json
     { schemaVersion, generatedAt, coreVersion, games[], result }
               │ FileSystemWatcher
               ▼
     GachaCalendar.exe（WPF, net10.0-windows）
     ├─ SnapshotStore → MainViewModel → DockStripWindow / FlyoutWindow
     ├─ TrayIcon / SettingsWindow
     └─ Taskbar + DockPositioner（Win32）
```

为什么 v0.1 不内置抓取：

- 抓取正确性可以独立验证（`npm run refresh` 输出逐条结果），不被 UI/窗口问题干扰；
- 应用启动不依赖网络，冷启动 < 2s；
- `snapshot.json` 是稳定契约，v0.1.7 换成内置 CoreHost 后 UI 一行不用改；
- 用户在没装 Node 的机器上也能先用示例快照看到完整界面（后续版本会内置）。

## 3. v0.1.7 目标数据流（应用内刷新）

```
GachaCalendar.exe
├─ Shell（WPF）
│   ├─ DockStripWindow / FlyoutWindow / SettingsWindow
│   ├─ TrayIcon、SingleInstance、Autostart、ThemeManager
│   └─ RefreshScheduler（启动判定 + 定时器 + 失败退避）
└─ CoreHost（隐藏 WebView2 页面，仅作 JS 引擎）
    ├─ import "gacha-calendar-core"（构建时内联 core.mjs）
    ├─ transport.fetchRaw / fetchViaProxy
    │     └─ postMessage → .NET HttpClient（可设 UA/Referer/Origin，无 CORS）
    ├─ storage.get/set
    │     └─ postMessage → .NET JSON 存储（配置 + 缓存）
    └─ refresh() → Result JSON → 写 snapshot.json → 通知 Shell
```

**为什么是隐藏 WebView2，而不是把 UI 也做成网页**：

- 常驻条要 1–2 秒轮询任务栏几何、不抢焦点、高 DPI 对齐，原生 WPF 更可控、更省内存；
- WebView2 只承担"跑 JS core"一件事，页面不可见，不参与渲染；
- Win11 自带 WebView2 Runtime（本机实测 155.x），无需打包浏览器内核；
- 未来若要换 Tauri/Electron，只换 Shell，CoreHost 的 bridge 语义不变。

> v0.1.7 的 transport 必须走原生 `HttpClient` 而不是页面 `fetch`：
> 部分源站需要自定义 `Referer`/`Origin`/`User-Agent`（浏览器页面禁止脚本设置 `Referer`），
> 否则会重蹈浏览器扩展里"必须靠 background 代发"的覆辙（见扩展 README §1、§2）。

## 4. 代码结构（v0.1）

| 路径 | 职责 |
|---|---|
| `src/GachaCalendar/App.xaml(.cs)` | 启动、单实例、托盘、定时器、窗口生命周期 |
| `src/GachaCalendar/Models/` | Snapshot / Result JSON / 设置的数据模型 |
| `src/GachaCalendar/Services/` | 路径与日志、设置存储、快照读取与监听、Win32 任务栏、窗口定位、主题、自启、单实例、托盘 |
| `src/GachaCalendar/ViewModels/` | `RowBuilder`（纯函数：JSON → 行文案）、`MainViewModel`（行/常驻条 chip）、`RowVm`、`ChipVm` |
| `src/GachaCalendar/Views/` | 常驻条、面板、设置三个窗口 |

## 5. 数据契约（摘要）

完整字段见 [06-数据契约](06-数据契约.md)。

- **Result JSON**：`schemaVersion=1`、`refreshedAt`、`parserVersions`、`games{id → record}`；
  record 的内容字段恒在（缺失为空串），状态字段为 `gachaFail` / `eventFail`（null | nomatch | down）、
  `gachaStale` / `eventStale`、`okAt`、可选 `skipped`。
- **本地快照**：在 Result JSON 外包一层 `games[]` 元信息（id/name/hidden/defaults）与
  `generatedAt` / `coreVersion`；`hidden` 已按 core 的 `hidden + defaultHidden + shown` 口径算好。
- **时间**：Result JSON 里的 `bannerDates` / `eventDates` 是**源站墙钟原文**（如 `10-13 18:00 ~ 11-03 14:59`）；
  UI 的倒计时按本机时区解释这串文本（与浏览器扩展同一口径）。
  海外用户看国服时的时区语义在 core 里已有 `tz` 建模，但 Result JSON 当前不输出绝对时间戳；
  若未来需要严格跨时区倒计时，应给 Result JSON 增加 `*EndTs` 字段并升 `schemaVersion`。

## 6. 可见性口径（容易错）

core 的隐藏规则是**三态**，不是单纯 `hidden` 数组：

```
hidden 里有 id           → 隐藏
defaultHidden 且 shown 里没有 → 隐藏
否则                     → 显示
```

`tools/refresh.mjs` 通过 `engine.__test.SOURCES` 读取 `defaultHidden`，按上述规则算好写进快照的 `hidden`。
v0.1.7 接入 CoreHost 后，设置页改显隐时必须同时维护 `hidden` 与 `shown` 两个键（参见扩展的 `visibility.js`），
否则会出现"勾了不生效 / 出厂隐藏项被放出来"的经典 bug。

## 7. 刷新与降级策略

v0.1：由用户/开发者运行 `cd tools; npm run refresh`；应用只读文件（被监听的快照变更后自动重载）。

v0.1.7（计划）：

- 启动时：若 `lastRefresh` 超过 `refreshHours`（默认 6h，可配 1–42 天）→ 后台刷一轮；
- 应用常驻期间：每小时检查一次"是否到点"；到点且未在刷新 → 刷；
- 失败退避：连续失败时指数退避（5min → 15min → 1h），避免源站故障期频繁请求；
- 并发保护：同一时刻只允许一轮 refresh（复用 core 自身的 `refreshInFlight`，UI 层再加锁）；
- 手动刷新按钮：面板右上角（v0.1.7 启用）；
- 降级：core 已实现"某列失败沿用上次成功值并标 stale"，UI 必须显示"沿用旧数据"与失败原因。

## 8. 生命周期与系统集成

| 项 | v0.1 行为 |
|---|---|
| 单实例 | `Local\GachaCalendar.SingleInstance.v1` Mutex；第二实例广播 `GachaCalendar.ShowPanel` 让第一实例展开面板后退出 |
| 托盘 | `NotifyIcon`；双击打开面板；菜单含显隐常驻条、设置、重读数据、退出 |
| 开机自启 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值名为 `GachaCalendar`；可在设置中关闭 |
| 退出 | 显式 `Shutdown`（`ShutdownMode=OnExplicitShutdown`）；关闭常驻条/面板不退出程序 |
| 数据目录 | `%LOCALAPPDATA%\GachaCalendar`（设置、快照、日志）；`GACHA_CALENDAR_DATA` 环境变量可指定快照路径（开发用） |
| 日志 | `%LOCALAPPDATA%\GachaCalendar\logs\app.log`，本地留存，不上传 |
| 高 DPI | PerMonitorV2；窗口位置用物理像素 `SetWindowPos`，尺寸按 `GetDpiForWindow` 换算 |
| 主题 | 启动时读 `AppsUseLightTheme`，动态替换画刷（v0.1.8 加系统事件监听） |

## 9. 安全与隐私

- **无服务端、无遥测、无账号**：用户数据只在本地。
- 网络请求只由 core 的来源表发起；自定义条目若由用户填 URL，v0.1.7 要限制为 `http(s)` 并拒绝私有网段/本机地址（防误用 SSRF）。
- 不读取游戏进程/内存，不注入游戏客户端，不修改游戏文件。
- 外部链接（后续版本"打开来源"）用系统默认浏览器打开，不在应用内嵌。

## 12. ADR（决策记录）

> 2026-10-21 补充：配置 / 快照 / Host 协议已抽到 `packages/engine/`（壳无关层），
> 详见 [07-壳无关基础层](07-壳无关基础层.md)。这样在外壳尚未拍板时，基础功能也不被阻塞。

| 编号 | 决策 | 原因 | 替代方案被否的原因 |
|---|---|---|---|
| ADR-001 | Windows Shell 用 **C# WPF（net10.0-windows）** | 本机可编译可运行，Win32 互操作直接；无 Rust/MSVC 工具链 | Tauri 需要 Rust + VS Build Tools，本机无法本地验证；Electron 体积/内存过大 |
| ADR-002 | 任务栏用**置顶覆盖窗**，不注入 explorer | 公开 API、更新不坏、杀软友好 | XAML 注入维护成本高（见 02） |
| ADR-003 | v0.1 **应用外抓取**，应用只读快照 | 先验证窗口/数据链路；契约与 v0.1.7 一致 | 一开始就写 WebView2 桥会让首版周期不可控 |
| ADR-004 | 抓取核心用 **npm 的 gacha-calendar-core**，不在本仓库 fork | 单一真源，解析器修复只改一处 | 复制解析器必然漂移 |
| ADR-005 | 常驻条用**原生 WPF** 绘制，不用 WebView2 渲染 | 高频轮询/DPI/焦点控制更稳，内存更低 | 网页 UI 在常驻条场景需要额外处理透明/点穿/输入法 |
