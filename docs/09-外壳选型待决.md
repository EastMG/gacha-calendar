# 09 · 外壳选型：待你拍板

> 2026-10-21 状态：**所有壳无关的基础功能已完成**（见 docs/04 的 v0.1.1–v0.1.6）。
> 继续往下做，第一步就必须决定 Windows 外壳用哪套技术；这份文档把选项、代价和现状列清楚。

## 1. 需要决定的只有一件事

**Windows 外壳用 WPF（当前原型）还是 Tauri v2？**

数据、配置、调度、校验、CLI、Host 协议、视图模型契约都已抽成壳无关层，
**换外壳不需要重写这些**。

## 2. 两条路线的现状与代价

| | A. 继续 WPF（当前） | B. 改用 Tauri v2 |
|---|---|---|
| 现有代码 | `src/GachaCalendar/` 已能编译运行：任务栏置顶条、面板、托盘、设置、单实例、自启 | 现有 C# 外壳全部作废（仅保留为交互/布局参考）；Rust + WebView2 重写 |
| 本机能否编译验证 | ✅ .NET 10 SDK 已装，`dotnet build` 可直接跑 | ❌ 本机没有 Rust / MSVC Build Tools；只能靠 CI 出包，迭代慢 |
| 复用壳无关层 | 直接读 snapshot；Host 可用 Node 子进程或 C# 实现同协议 | 直接 import `packages/engine` / `packages/viewmodel`，前端复用 |
| 跨平台桌面 | 仅 Windows（本产品任务栏本来就是 Windows 专属） | macOS/Linux 也能跑（但任务栏形态要另做） |
| 包体积/内存 | 框架依赖小；自包含 ~80MB；内存与 Tauri 接近（都依赖 WebView2/系统组件） | 安装包更小；但 Windows 仍依赖 WebView2 |
| 长期维护 | C# + Win32 互操作，AI/人均可读 | Rust 门槛更高；但前端是 Web 技术，UI 改起来快 |
| 移动端 | 不涉及（Android/iOS 本来就走 core 另写原生） | Tauri v2 可出 Android/iOS，但任务栏小组件不适用移动端 |

## 3. 我的建议

**如果没有"macOS/Linux 桌面版"的近期计划，建议继续 WPF**：

1. 本机可编译、可运行、可截图验证，迭代成本最低；
2. 任务栏停靠是 Windows 专属的 Win32 工作，Tauri 里同样要写 Rust 调 Win32，省不掉；
3. 壳无关层已抽好，将来真要上 macOS/Linux，再把 UI 迁到 Tauri 也不会阻塞 Windows 版。

**如果希望"一套 Web UI 同时覆盖 Windows/macOS/Linux"**，选 Tauri：
壳无关层可以直接复用，主要成本是重写窗口/托盘/任务栏和安装 Rust 工具链。

## 4. 拍板后立刻能做的（都需要外壳）

- 任务栏常驻条接入 Host：`refreshIfDue` / `getStatus` / `updateConfig`；
- 设置页：`entries` + `setEntryVisibility` / `setOrder` / `removeEntry` / `restoreEntry`；
- 托盘、单实例、开机自启、DPI、多显示器、全屏让位；
- 安装包、签名、更新检测。

## 5. 不做的事

- 不为了"技术先进"把已经能跑的 WPF 外壳推倒重来；
- 不在外壳未定时继续写两套 UI；
- 不在没有明确指令时打 tag / 发 Release。
