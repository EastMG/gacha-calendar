# 10 · Windows 外壳技术方案对比

> 调研/评估时间：2026-10。比较对象：WPF、WPF + WebView2、WinUI 3、Tauri v2、Electron、Avalonia、WinForms，
> 以及 Flutter / MAUI / 原生 C++ 这类"可行但不推荐"的路线。
>
> 结论先行：**Windows 任务栏小组件这个形态，当前最优仍是 WPF**；如果"跨平台桌面"是近期目标，
> 第二选择是 **Tauri v2**；WinUI 3 只在"Fluent UI + Microsoft Store 优先"时值得考虑，
> 不适合作为任务栏覆盖窗的第一选择。

## 1. 本项目的硬约束（评分权重来源）

| 约束 | 说明 | 权重 |
|---|---|---|
| 任务栏覆盖窗 | 无边框、置顶、不抢焦点、不进 Alt+Tab、跟随任务栏几何/DPI/自动隐藏 | 25% |
| 本地可构建/可验证 | 改完能立刻编译、运行、截图；不能只靠 CI | 20% |
| 复用既有资产 | `packages/engine`（Node/JS）、`packages/viewmodel`（JS）、现有 C# 逻辑 | 15% |
| 包体积 / 内存 | 常驻小程序，不能像 Electron 那样吃 200MB+ | 10% |
| 跨平台未来 | macOS/Linux 桌面；Android/iOS 另算（任务栏不适用） | 10% |
| 开发/维护成本 | 单人 + AI 维护，28 个来源长期迭代 | 10% |
| 分发/签名/商店 | MSIX/安装包、SmartScreen、商店审核 | 10% |

## 3. 逐个方案

### 3.1 WPF（当前原型）

**适合**：Windows-only、需要原生任务栏/托盘/DPI 控制、要本地可验证。

- 任务栏：已在本仓库实测——`Shell_TrayWnd` 定位、`WS_EX_NOACTIVATE`、topmost、PerMonitorV2；
- 托盘：`NotifyIcon` 直接用；单实例/自启：几行 P/Invoke/注册表；
- 数据：直接读 `snapshot.json`；`packages/engine` 可作为 Node sidecar；
- 缺点：UI 是 XAML，视觉上不如 WinUI/Fluent 现代；跨平台为零；
- 体积：框架依赖 ~2MB（需 .NET 10 Desktop Runtime），自包含 ~70–80MB；无 WebView2 时内存低。
- **结论：当前最稳，继续做不需要任何新工具链。**

### 3.2 WPF + WebView2（混合）

**适合**：想直接复用浏览器扩展的 HTML/CSS/JS 和 `packages/viewmodel`，同时保留 WPF 的任务栏/托盘能力。

- 外壳（WPF）负责窗口/任务栏/托盘；面板内容用 WebView2 加载本地 HTML；
- 隐藏 WebView2 还可作为 JS 引擎跑 `gacha-calendar-core`（v0.1.7 计划）；
- 代价：多一个 WebView2 渲染进程（内存 +80–150MB）、透明/无激活窗口与 WebView2 组合需要额外验证；
- **结论：如果"UI 复用"优先级高于"内存/简单"，这是 WPF 路线里最务实的增强，而不是换外壳。**

### 3.3 WinUI 3（Windows App SDK）

**适合**：要 Fluent 设计、Windows 11 原生控件、MSIX/Microsoft Store 优先的常规桌面应用。

- 优点：现代控件/主题、Windows 11 观感最好；Microsoft Store 通道顺；
- 任务栏覆盖窗代价高：
  - 无内置托盘图标（要 Win32 `Shell_NotifyIcon` 或第三方）；
  - 无边框、透明、`WS_EX_NOACTIVATE`、点击穿透需要 Win32 互操作；
  - 透明窗口 + XAML Island 的已知限制比 WPF 多，社区案例少；
- 工程链：Windows App SDK NuGet + XAML 编译器 + MSIX/未打包两种部署；
  本机 NuGet 还原曾出现 SSL/凭据问题，WinUI 的依赖面比 WPF 大；
- **结论：常规桌面应用值得选；"任务栏覆盖窗"这个形态不建议作为首选。**

### 3.4 Tauri v2

**适合**：希望一套 Web UI 同时覆盖 Windows/macOS/Linux，且能接受 Rust 工具链。

- 优点：体积小（几 MB + 系统 WebView2）、前端直接复用 `packages/viewmodel`/HTML；
- 现成能力：tray、autostart、single-instance、global-shortcut、updater 等插件；
- 任务栏：仍然要写 Rust 调 Win32（窗口样式、任务栏矩形、DPI），这部分和 WPF 的工作量同级；
- 门槛：本机没有 Rust + MSVC Build Tools；只能靠 CI 出包，迭代反馈慢（这是当前最大问题）；
- **结论：跨平台桌面是真实需求时选它；否则为了"技术现代"重写外壳不划算。**

### 3.5 Electron

**适合**：完全复用 Web 技术、接受 100MB+ 体积/内存的常规桌面应用。

- 任务栏/托盘：`BrowserWindow` + `Tray` + `setAlwaysOnTop` + 原生窗口样式；
- 优点：UI 开发最快、生态成熟、跨平台；
- 缺点：对"常驻任务栏的小组件"来说太重；启动慢、内存高；
- **结论：能最快做出来，但不适合作为长期形态。**

### 3.6 Avalonia

**适合**：想用 C#/XAML、又要 Windows/macOS/Linux 三平台桌面。

- 优点：C# 复用现有 ViewModel 思路；XAML 风格接近 WPF；跨平台；
- 缺点：任务栏覆盖窗仍需 Win32 互操作；包依赖 NuGet（本机还原有风险）；生态/案例少于 WPF；
- **结论：如果"跨平台桌面 + C#"同时成立，可作为 Tauri 之外的第二选择。**

### 3.7 WinForms

**适合**：只想要托盘 + 简单面板，不追求现代 UI。

- 优点：最直接、最稳、本机可验证；托盘内置；任务栏定位同样是 P/Invoke；
- 缺点：UI 观感/布局能力弱；当前 WPF 面板已经写好，回退 WinForms 是负收益；
- **结论：只作为"极简兜底"参考，不替换现有 WPF。**

### 3.8 不推荐路线

| 方案 | 原因 |
|---|---|
| Flutter Desktop | 要重写 UI（Dart），任务栏覆盖靠插件/FFI；JS core 不能直接复用 |
| .NET MAUI | Windows 目标就是 WinUI 3，任务栏场景更绕；移动端收益与任务栏无关 |
| 原生 C++/Rust Win32 | 控制力最强，但 UI/迭代成本高；本机无 MSVC；还要嵌 JS 引擎才能跑 core |
| PWA | 无法常驻任务栏；只能做网页日历 |
| 官方 Widgets Board Provider | 只能出现在 Win+W 面板，不是任务栏常驻；可作为第二入口，不是外壳 |

## 4. 决策建议

### 推荐顺序

1. **默认：继续 WPF**（当前原型 + 壳无关层）——本地可验证、任务栏已跑通、无新工具链；
2. **若"macOS/Linux 桌面版"是 6–12 个月内的真实目标：Tauri v2**——先装 Rust + MSVC Build Tools，
   把"CI 出包 + 本地开发"跑通再迁；壳无关层可全部复用；
3. **若"Fluent UI + Microsoft Store"优先：WinUI 3**——但任务栏覆盖窗要单独做技术验证（透明/无激活/托盘）；
4. **若"复用扩展 UI"优先但仍想留 C# 外壳：WPF + WebView2**——不是换外壳，是增强。

### 一句话

- **Windows 任务栏小组件 = WPF 最匹配**；
- **Tauri 的价值在跨平台桌面，不在 Windows 任务栏本身**；
- **WinUI 3 适合常规窗口应用，不适合作为覆盖任务栏的第一选择**；
- Electron / Flutter / MAUI / 原生 C++ 都不解决"任务栏 + 小组件"的核心问题，反而增加成本。
